# 开发验证与工具反馈指南

本文档补充 `.cursor/rules/feedback-validation.mdc`，用于指导 agent 团队在自主开发时像真实团队一样持续拿到运行反馈。

## 验证分层

- L0 静态检查：语法检查、lint、配置检查、资源路径检查。适合所有代码和配置改动。
- L1 浏览器冒烟：本地启动游戏，确认页面打开、Canvas 渲染、无明显控制台错误。
- L2 核心流程：用 Playwright 或等价自动化覆盖建造、移动、采矿、敌袭、胜败、重开等关键路径。
- L3 发布验证：对 `Releases/<version>/` 的归档版本重新运行冒烟或核心流程，并记录已知问题。

## 任务类型建议

- 文档、规则、PM 看板：检查内容是否与现有规则冲突，确认没有误改代码或发布产物。
- UI、HUD、Canvas 表现：运行浏览器验证，必要时保留截图；检查控制台错误。
- 玩法、数值、状态机：至少做脚本/自动化验证和一次浏览器/实机体验验证。
- 输入、坐标、交互：优先用 Playwright 录入点击路径，失败时保留 trace、截图或日志。
- 发布任务：验证归档目录可运行，版本说明包含 commit/tag、构建时间、已知问题和后续方向。

## 反馈产物约定

- 临时测试产物统一放入 `Artifacts/`、`test-results/` 或工具默认报告目录，并通过 `.gitignore` 排除。
- Guard 运行日志和游戏测试产物分开管理；不要把截图、录像、trace 或大段日志塞进 Guard 日志。
- PM 看板只记录验证摘要和必要路径，不粘贴大体积日志。
- 发布版本只挑选少量有长期价值的截图、录像或说明归档，其余临时产物不提交。

## Playwright 使用时机

- 新增或修改核心交互后，应优先补一条冒烟或回归用例。
- 当同一流程需要反复人工点击验证时，应工具化。
- 当 Bug 依赖复杂状态重现时，应用脚本搭建状态或记录重现路径。
- Playwright 不是唯一选择；只要能稳定获得浏览器运行、控制台和交互反馈，也可以使用其他等价工具。

## 工具链升级判断

当前原型优先保持轻量。只有当工具问题影响可玩性迭代时，才评估引擎、插件或构建管线。

常见触发信号：

- 单文件逻辑膨胀、状态难以追踪、回归测试成本过高。
- 需要复杂物理、碰撞、动画、粒子、音频或资源管理。
- UI 状态和交互分支明显超过手工验证能力。
- 发布归档、路径、依赖或浏览器兼容问题反复出现。

评估新工具时必须说明：收益、成本、替代方案、许可证、运行负担、迁移风险、回滚方案和最小试点范围。
